## 1. Purpose and Context

This document is a complete, self-contained specification for the RQIS Streamlit dashboard. It is written so that a developer or agent with no prior session context can implement the full dashboard from scratch.

The dashboard serves two roles:

1. **The universal C1 gate.** Every broker order submission — paper or live — must pass through the Blotter Approval page (Page 4). The CLI confirmation workflow (`paper_approve_blotter.py --confirm YES`) is the current interim path and is replaced by this dashboard once it is live. This is the highest-priority page.

2. **The operational observation layer.** Prior to this dashboard, the system has no integrated view. An operator running the paper trading qualification must stitch together CLI script output, local JSON artifacts, and Airflow logs to understand system state. The dashboard provides a single screen from which the entire trading lifecycle is observable.

### What this dashboard is NOT

- It is not a trading terminal. It does not replace TWS/Gateway.
- It is not a public-facing product. It is an internal operator tool for a solo operator.
- It is not a report generator. Tearsheet PDFs are generated by the `report` skill separately; the dashboard links to them.
- It does not support live trading execution until C8 clearance (4-week paper qualification) is complete. The live trading execution path exists in the codebase but the dashboard must not enable it until C8 is cleared.

## 2. Technology Stack

| Component | Choice | Rationale |
|-----------|--------|-----------|
| UI framework | **Streamlit** | Pure Python — dashboard pages call existing Python modules directly (RiskMonitor, TradeJournal, metrics.py) with no REST API or serialization layer required |
| Database | **TimescaleDB / PostgreSQL** via SQLAlchemy | Matches existing infra; all tables already defined |
| Charts | **Matplotlib** via `st.pyplot()` | `reporting/tearsheets/charts.py` already returns Matplotlib figures |
| Tabular data | `st.data_editor` | Supports editable cells and per-row checkboxes (required for blotter approval) |
| Secrets | `st.secrets` + `os.environ` | Never hardcode credentials (C5) |
| Scheduling/refresh | `st.rerun()` with `time.sleep()` in a loop | Auto-refresh for risk monitor; Streamlit does not support server-push |

## 4. Prerequisites — Backend Work Required Before Full Dashboard

Two small backend pieces must be built alongside (not before) the dashboard. They do not block most pages but are required for specific features.

### 4.1 `portfolio_snapshots` Table and Airflow Task Change

**Blocks:** Page 2 (Positions) live position data.

**Why:** The dashboard should not make its own IBKR connection. The Airflow DAG's `fetch_ibkr_snapshot` task already pulls current positions from IBKR every night. A minor change to that task writes the snapshot to the DB, which the dashboard then reads.

**Schema:**

```sql
CREATE TABLE portfolio_snapshots (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    snapshot_date   DATE NOT NULL,
    strategy_id     TEXT NOT NULL,
    dag_run_id      TEXT NOT NULL,
    fetched_at_utc  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    cash_usd        NUMERIC(18,6) NOT NULL,
    positions       JSONB NOT NULL,
    nav_usd         NUMERIC(18,6) NOT NULL,
    source          TEXT NOT NULL DEFAULT 'ibkr_paper'
);
CREATE INDEX ON portfolio_snapshots (snapshot_date DESC, strategy_id);
```

`positions` is a JSON array of `{"ticker": "AAPL", "quantity": 10.0, "avg_cost": 185.42, "current_price": 191.10}`.

**Airflow change:** In `daily_paper_trading.py`, after `fetch_ibkr_snapshot` fetches positions from IBKR, add an INSERT to `portfolio_snapshots` using the same data. The XCom artifact is retained unchanged.

**Fallback:** If no snapshot exists for today, Page 2 reconstructs positions from `trade_fills` using `TradeJournal.open_position_cost_basis()` and prices from `daily_prices`. This is the fallback for the paper qualification period before Airflow has run.

### 4.2 `strategy_simulations` Table and Forward Simulation Task

**Blocks:** Strategy comparison panel on Page 5 (forward simulation returns only; historical MLflow backtests are available immediately).

**Why:** Once the live paper portfolio starts, we need to know how each shadow (non-live) VALIDATED strategy *would have* performed over the same period. Historical MLflow backtests stop at paper trading inception. This task extends them forward daily.

**Schema:**

```sql
CREATE TABLE strategy_simulations (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    strategy_id     TEXT NOT NULL,
    sim_date        DATE NOT NULL,
    target_weights  JSONB NOT NULL,
    simulated_return NUMERIC(12,8) NOT NULL,
    simulated_nav   NUMERIC(18,6) NOT NULL,
    universe_size   INTEGER NOT NULL,
    n_positions     INTEGER NOT NULL,
    computed_at_utc TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (strategy_id, sim_date)
);
CREATE INDEX ON strategy_simulations (sim_date DESC, strategy_id);
```

**New Airflow task** in `daily_signal_pipeline.py` (runs after all strategy scores are computed):

```
For each strategy with status IN ('ACTIVE', 'VALIDATED') in strategy_registry:
    1. Read latest alpha_scores for this strategy
    2. Apply strategy's portfolio construction parameters (n_long, max_weight)
    3. Compute target weights (equal weight top N, or strategy-specified method)
    4. Fetch daily_prices.close for today for each ticker in target
    5. Compute weighted daily return
    6. Update simulated_nav = prev_nav * (1 + simulated_return)
    7. UPSERT into strategy_simulations
```

The active live strategy is also tracked here for consistent comparison (its simulated NAV will match the real NAV only approximately, since it excludes transaction costs and fill slippage).

### 4.3 `quantity_overrides` Column on `blotter_approvals` — **RESOLVED: New JSONB column**

**Decision (2026-06-29):** Add a `quantity_overrides JSONB` column to `blotter_approvals`. The existing `selected_order_ids` column (array of approved order ID strings) is unchanged. Quantity edits are stored separately.

**Alembic migration required before Sprint 1:**

```python
# infra/db/migrations/versions/xxxx_add_quantity_overrides_to_blotter_approvals.py
def upgrade():
    op.add_column(
        "blotter_approvals",
        sa.Column("quantity_overrides", postgresql.JSONB, nullable=True)
    )

def downgrade():
    op.drop_column("blotter_approvals", "quantity_overrides")
```

`quantity_overrides` stores only the orders where the operator changed the quantity: `{"order_id_abc": 7, "order_id_def": 4}`. Orders with no quantity change are absent from this dict. An empty dict or NULL means no quantities were edited.

**Airflow `submit_orders` task change:** The task must read both `selected_order_ids` and `quantity_overrides` from the approval row and apply overrides before submitting to IBKR. Orders in `selected_order_ids` but absent from `quantity_overrides` use the original blotter quantity.

### 4.4 Blotter Artifact Location — **RESOLVED: Shared Docker volume** — **RESOLVED: Shared Docker volume**

**Decision (2026-06-29):** Shared Docker volume (Option A).

**Implementation:** Add a named volume `rqis_paper_artifacts` to `docker-compose.yml`. Mount it in the Airflow container (read-write) and the dashboard container (read-only) at the same path (`/opt/rqis/paper_artifacts`). The dashboard reads the blotter JSON file at the path stored in `blotter_approvals.blotter_local_path`. No schema changes required.

```yaml
# docker-compose.yml addition
volumes:
  rqis_paper_artifacts:

services:
  airflow-worker:
    volumes:
      - rqis_paper_artifacts:/opt/rqis/paper_artifacts
  dashboard:
    volumes:
      - rqis_paper_artifacts:/opt/rqis/paper_artifacts:ro
```

The `RQIS_PAPER_ARTIFACT_DIR` env var must be set to `/opt/rqis/paper_artifacts` in both containers. The file remains the authoritative source for SHA-256 integrity checking — the hash is computed over bytes-on-disk, not a DB round-trip.

**Future migration path:** If the dashboard is ever moved to a remote host, migrate to JSONB storage via an Alembic migration at that time. No code changes to the approval logic are needed — only the artifact-loading path in `queries.py` changes.

## 5. Shared Components

These run on every page. They are rendered in `app.py` before the page router loads.

### 5.1 Environment Banner (`components/env_banner.py`)

Reads `PAPER_TRADING` env var and `IBKR_PORT` env var at app startup. Renders a full-width colored banner at the top of every page:

- `PAPER_TRADING=true`, port 7497 → **green banner:** `PAPER TRADING ACTIVE — Port 7497`
- `PAPER_TRADING=false`, port 7496 → **red banner:** `⚠ LIVE TRADING ACTIVE — Port 7496`
- Any other combination → **red banner:** `⚠ ENVIRONMENT MISCONFIGURED — Check PAPER_TRADING and IBKR_PORT`

The banner cannot be dismissed or hidden. It is the PRD F7.4 requirement that the operator always knows which environment they are approving into.

### 5.2 Circuit Breaker Status Widget (`components/circuit_breaker.py`)

Rendered in the sidebar on every page. Reads `CircuitBreaker.status_dict()`.

- CLOSED → small green badge: `Circuit Breaker: CLOSED ✓`
- OPEN → large red badge with trip reason and timestamp: `CIRCUIT BREAKER OPEN — [metric] breached [value] at [time]`

When OPEN, all pages display a non-dismissable warning banner below the env banner: `Trading is halted. No orders can be submitted until the circuit breaker is reset by the operator.`

### 5.3 Pending Blotter Badge

Sidebar shows a red badge `● Blotter awaiting approval` whenever a row exists in `blotter_approvals` that has not yet been confirmed (i.e., `confirmed_blotter_sha256 IS NULL`). Clicking the badge navigates to Page 4.

### 5.4 Session State Initialization (`app.py`)

On every cold start:

```python
if "session_id" not in st.session_state:
    st.session_state["session_id"] = str(uuid.uuid4())
if "operator_email" not in st.session_state:
    st.session_state["operator_email"] = os.environ.get("OPERATOR_EMAIL", "unknown")
```

`session_id` is passed to `blotter_approvals.dashboard_session_id` at approval time. `operator_email` is passed to `blotter_approvals.approved_by`.

## 6. Page Specifications

### Page 1 — Overview

**File:** `pages/1_Overview.py`  
**Purpose:** Immediate system state at a glance. Designed for the 23:05 ET check: "Did the pipeline run? Is approval needed?"  
**Refresh:** Auto-refresh every 60 seconds using `st.rerun()`.  
**IBKR connection:** Not required. All data from DB.

**Sections:**

| Section | Data source | Query |
|---------|-------------|-------|
| NAV (today vs. yesterday) | `portfolio_snapshots` | Latest two rows by `snapshot_date DESC` |
| Drawdown from peak | `portfolio_snapshots` | Compute from NAV history: `(current_nav / max(nav_usd)) - 1` over all rows |
| Open positions count | `portfolio_snapshots.positions` | `len(positions)` from latest snapshot |
| Pending blotter | `blotter_approvals` | `SELECT COUNT(*) WHERE confirmed_blotter_sha256 IS NULL` |
| Pipeline health | `alpha_scores`, `daily_prices`, `strategy_simulations` | Data recency inference — see below |
| Active alerts | `AlertManager.unacknowledged()` | In-memory; AlertManager must be instantiated at app startup and shared via `st.session_state` |

**Pipeline health — RESOLVED: Infer from data recency (D3, 2026-06-29).**

No direct Airflow metadata DB connection. Pipeline health is inferred from the freshness of the data each pipeline produces:

```python
# queries.py
def pipeline_health(engine) -> dict:
    with engine.connect() as conn:
        prices_age = conn.execute(text(
            "SELECT NOW() - MAX(ingested_at) FROM daily_prices"
        )).scalar()
        scores_age = conn.execute(text(
            "SELECT NOW() - MAX(computed_at) FROM alpha_scores"
        )).scalar()
        sim_age = conn.execute(text(
            "SELECT NOW() - MAX(computed_at_utc) FROM strategy_simulations"
        )).scalar()
    return {
        "prices": {"age": prices_age, "ok": prices_age < timedelta(hours=28)},
        "signals": {"age": scores_age, "ok": scores_age < timedelta(hours=6)},
        "simulations": {"age": sim_age, "ok": sim_age < timedelta(hours=6)},
    }
```

Display as a three-row status table: pipeline name, last updated (human-readable "2 hours ago"), status badge (✓ Fresh / ⚠ Stale). Thresholds: prices stale after 28 hours (allows for next-day ingestion window); signals and simulations stale after 6 hours (should run by 23:30 ET). For more detailed DAG-level diagnosis, the operator uses the Airflow UI directly.

**Layout:** Two rows of `st.metric()` cards, then a `st.dataframe()` for the alert list, then a pipeline status table.

### Page 2 — Positions & P&L

**File:** `pages/2_Positions.py`  
**Purpose:** What do we own, what did it cost, what is it worth.  
**Refresh:** Manual (button). Positions data is at most one trading day stale.  
**IBKR connection:** Not required. Reads from `portfolio_snapshots` and `alpha_scores`.

**Sections:**

**Holdings table** (`st.dataframe`, sortable):

| Column | Source |
|--------|--------|
| Ticker | `portfolio_snapshots.positions[].ticker` |
| Quantity | `portfolio_snapshots.positions[].quantity` |
| Avg cost | `portfolio_snapshots.positions[].avg_cost` (from TradeJournal FIFO, stored in snapshot) |
| Last price | `daily_prices.close` for latest date |
| Unrealized P&L ($) | `(last_price - avg_cost) * quantity` |
| Unrealized P&L (%) | `(last_price / avg_cost) - 1` |
| Weight (%) | `(last_price * quantity) / nav_usd` |
| Alpha score rank | `alpha_scores.rank` for latest `score_date`, matching `strategy_id` |
| Alpha score value | `alpha_scores.alpha_score` |

Rows highlighted amber where `alpha_score_rank > n_long * 1.5` (position held but signal has degraded significantly — potential sell candidate at next rebalance).

**Realized P&L summary** (`st.dataframe`):
- Query `trade_fills` grouped by ticker for `side = 'SELL'`: `SUM(realized_pnl)` by ticker, YTD.
- Highlight red where `realized_pnl < 0` and `wash_sale_disallowed = true`.

**Cost basis detail** (expandable section):
- `TradeJournal.open_position_cost_basis(strategy_id=active_strategy)` → FIFO cost basis per share per position.

**Strategy selector:** Dropdown at top of page (`SELECT DISTINCT strategy_id FROM portfolio_snapshots`). Defaults to the active live strategy.

### Page 3 — Risk Monitor

**File:** `pages/3_Risk.py`  
**Purpose:** Real-time risk metrics. The page that should alarm you.  
**Refresh:** Auto-refresh every 30 seconds during market hours (09:30–16:00 ET). Pauses overnight.  
**IBKR connection:** Not required. Risk metrics computed from DB data.

**Risk computation:** Call `RiskMonitor.snapshot()` with:
- `as_of`: today's date
- `nav`: from latest `portfolio_snapshots.nav_usd`
- `weights`: from latest `portfolio_snapshots.positions` (normalized weights)
- `portfolio_returns`: from `trade_fills` implied daily returns OR from `strategy_simulations.simulated_return` for the active strategy
- `asset_returns`: from `daily_prices` for portfolio tickers, last 252 days
- `benchmark_returns`: from `daily_prices` for SPY, last 252 days

**Sections:**

| Section | Display | Hard threshold | Warn threshold |
|---------|---------|---------------|----------------|
| 1-day VaR 99% | `st.metric()`, red if breached | 2.5% of NAV | 1.5% |
| CVaR 99% | `st.metric()` | — | — |
| Drawdown from peak | `st.metric()`, colored gauge | -10% | -5% |
| Portfolio beta | `st.metric()` | 1.5 | 1.2 |
| Max single-name concentration | `st.metric()` | 5% | 3.5% |
| Max sector concentration | `st.metric()` | 25% | 20% |

When any hard threshold is breached, a `st.error()` banner renders above the metrics: `HARD BREACH: [metric] = [value] (threshold: [limit])`.

**Alert feed** (below metrics):
- `AlertManager.unacknowledged()` rendered as `st.warning()` or `st.error()` per severity.
- "Acknowledge" button per alert calls `AlertManager.acknowledge(alert_id)`.
- Acknowledged alerts shown below in a collapsed `st.expander`.

**Circuit breaker controls** (admin section, below alerts):
- If `CircuitBreaker.is_closed`: show status only, no controls.
- If `CircuitBreaker.is_open`: show trip history table + reset form.
  - Reset form: two fields — `Operator ID` (text, pre-filled from `session_state.operator_email`) and `Reason code` (text, required, min 10 chars).
  - "Reset circuit breaker" button calls `CircuitBreaker.reset(operator, reason_code)`.
  - Before calling reset, render `st.warning()`: `"This will re-enable order submission. Are you sure?"` with a second "Confirm Reset" button (C4 enforcement — two-step, C9 pattern).
  - Reset is logged; the sidebar CB widget updates on next refresh.

### Page 4 — Blotter Approval *(C1 Gate)*

**File:** `pages/4_Blotter_Approval.py`  
**Priority:** Highest. This page must be complete before the automated paper pipeline can replace the CLI approval path.  
**Safety rules enforced:** C1, C3, C5, C9.  
**IBKR connection:** Not required (reads blotter artifact; Airflow handles IBKR submission).

**Page states:**

#### State A — No pending blotter

```
No blotter is awaiting approval.
The Airflow DAG runs at 23:00 ET on trading days.
Last DAG run: [timestamp] — [status]
```

Detect: `SELECT COUNT(*) FROM blotter_approvals WHERE confirmed_blotter_sha256 IS NULL` = 0.

#### State B — Blotter awaiting approval

**Step 1: Blotter header** (read-only info block):

| Field | Value |
|-------|-------|
| Run ID | `blotter_approvals.blotter_run_id` |
| Generated at | `blotter artifact: generated_at_utc` |
| Environment | `PAPER TRADING` or `LIVE TRADING` (from blotter artifact `paper_only` flag) |
| IBKR Port | From env var (displayed prominently) |
| SHA-256 fingerprint | `blotter_approvals.blotter_sha256` (first 16 chars displayed; full hash available on hover) |
| Strategy | From blotter artifact |
| Total orders | Count of candidate rows |
| Total notional | Sum of `estimated_notional` across all rows |

**Step 2: Load and verify blotter artifact:**

```python
# Resolve artifact path
artifact_path = row["blotter_local_path"]  # from blotter_approvals row

# Load JSON
with open(artifact_path) as f:
    blotter = json.load(f)

# Verify SHA-256 matches what Airflow recorded
computed_hash = hashlib.sha256(
    open(artifact_path, "rb").read()
).hexdigest()

if computed_hash != row["blotter_sha256"]:
    st.error("INTEGRITY CHECK FAILED: Blotter file has been modified since it was generated.")
    st.stop()
```

If SHA-256 mismatch: render error, do not show order grid, do not enable any submission controls.

**Step 3: Order grid** (`st.data_editor`):

| Column | Type | Editable? | Notes |
|--------|------|-----------|-------|
| ✓ (select) | Checkbox | Yes | Default: all checked |
| Ticker | Text | No | — |
| Side | Text | No | BUY or SELL |
| Quantity | Number | **Yes** | Operator may reduce (not increase) |
| Limit price | Number | No | From blotter artifact |
| Est. notional | Number | No | Auto-computed: `quantity * limit_price` |
| Est. transaction cost | Number | No | From `execution/cost_model/estimator.py` |
| Risk flag | Text | No | `CONCENTRATION` if position would breach limit post-trade; blank otherwise |

Rows with risk flags are highlighted amber. Rows with `side = SELL` are highlighted light blue.

Running totals below grid:
- "Selected: [N] orders / $[X] notional"
- "Deselected (will be rejected): [M] orders / $[Y] notional"

**Quantity edit validation:**
- Edited quantity must be `> 0` and `≤ original quantity`. If operator increases quantity, revert to original and show `st.warning("Quantity may not be increased from the blotter value.")`.

**Step 4: Submission flow:**

"Submit selected orders" button is disabled if:
- Circuit breaker is OPEN (C4)
- SHA-256 verification failed
- No rows are selected
- `PAPER_TRADING` env var is not `"true"` AND port is not 7497 (safety guard for paper qualification period)

On button click, render confirmation dialog using `st.dialog` (Streamlit 1.32+) or `st.warning` + checkbox pattern:

```
You are about to submit [N] orders totalling $[X] notional to
IBKR PAPER (port 7497).

Strategy: v1_base_momentum
Run ID: [run_id]

Deselected orders ([M]) will be permanently recorded as operator-rejected.

This action cannot be undone.
```

Operator must check a checkbox: `"I have reviewed all orders and confirm this submission."` Then click "CONFIRM SUBMISSION".

**On confirmation:**

```python
# 1. Re-verify SHA-256 at submission time (not just at page load)
confirmed_hash = hashlib.sha256(open(artifact_path, "rb").read()).hexdigest()
if confirmed_hash != row["blotter_sha256"]:
    st.error("Blotter file changed between review and submission. Aborting.")
    st.stop()

# 2. Resolve selected order IDs from checkbox state
selected_ids = [row["order_id"] for row in edited_df if row["selected"]]

# 3. Quantity overrides (where operator edited)
quantity_overrides = {
    row["order_id"]: row["quantity"]
    for row in edited_df
    if row["quantity"] != original_quantities[row["order_id"]]
}

# 4. INSERT into blotter_approvals
with db.engine.begin() as conn:
    conn.execute(
        text("""
            UPDATE blotter_approvals
            SET selected_order_ids = :selected_ids,
                confirmed_blotter_sha256 = :confirmed_hash,
                approved_by = :approved_by,
                dashboard_session_id = :session_id,
                quantity_overrides = :overrides,
                approved_at_utc = NOW()
            WHERE blotter_run_id = :run_id
              AND confirmed_blotter_sha256 IS NULL
        """),
        {
            "selected_ids": json.dumps(selected_ids),
            "confirmed_hash": confirmed_hash,
            "approved_by": st.session_state["operator_email"],
            "session_id": st.session_state["session_id"],
            "overrides": json.dumps(quantity_overrides),
            "run_id": row["blotter_run_id"],
        }
    )
```

Note: `quantity_overrides` is a new JSONB column on `blotter_approvals` — see Section 4.4 for the required Alembic migration.

**Step 5: Post-submission receipt:**

Page transitions to a read-only receipt:

### Page 5 — Performance

**File:** `pages/5_Performance.py`  
**Purpose:** How is the strategy performing over time, and how does it compare to shadow strategies.  
**Refresh:** Manual.  
**IBKR connection:** Not required.

**Date range selector:** `YTD / 3M / 6M / 1Y / All` (default: YTD).

**Section A: Live strategy metrics**

Compute using `reporting.tearsheets.metrics.compute_metrics()` with returns derived from `trade_fills` (for the live strategy) or `strategy_simulations.simulated_return` (for shadow).

Display as `st.metric()` cards in a 4-column grid:
- Total Return, CAGR, Sharpe Ratio, Sortino Ratio
- Max Drawdown, Calmar Ratio, Information Ratio
- Beta (vs SPY), Alpha (Jensen's), Volatility (annualized)
- Number of trades, Average transaction cost

**Section B: Charts**

Each chart rendered with `st.pyplot()`:
1. `charts.equity_curve()` — strategy vs. SPY benchmark
2. `charts.drawdown_underwater()` — drawdown series
3. `charts.monthly_returns_pivot()` — monthly return heatmap (year × month)
4. `charts.rolling_sharpe()` — 252-day rolling Sharpe
5. `charts.annual_returns()` — year-by-year bar chart

**Section C: Strategy Comparison**

Strategy selector: multi-select of all strategies with status IN ('ACTIVE', 'VALIDATED') from `strategy_registry`. Default: all.

For each selected strategy, compute the same metrics suite from either:
- `strategy_simulations` (forward simulation since paper trading inception)
- MLflow (historical backtest — fetched via MLflow client `get_run()` / `search_runs()`)

The two sources are concatenated into a single return series per strategy: MLflow historical → `strategy_simulations` forward.

**Comparison table** (sortable `st.dataframe`):

| Strategy | Status | Source | Return | Sharpe | Max DD | VaR 99% | Beta | Concentration |
|----------|--------|--------|--------|--------|--------|---------|------|---------------|
| v1_base_momentum | LIVE | Real fills | 8.2% | 0.91 | -9.4% | 1.8% | 0.82 | 6.1% |
| v2_value_quality | VALIDATED | Simulated | 11.4% | 1.24 | -7.1% | 1.4% | 0.71 | 5.3% |
| v3_low_vol | VALIDATED | Simulated | 6.1% | 1.47 | -4.2% | 0.9% | 0.51 | 8.2% |

**Risk metrics for shadow strategies** are computed using `RiskMonitor`-compatible functions from `metrics.py` applied to `strategy_simulations` daily returns and `target_weights`. VaR and CVaR computed from the simulated return distribution. Beta computed against SPY returns from `daily_prices`. Concentration from `target_weights` JSON.

**Equity curve overlay:** A single chart showing all selected strategy equity curves together (strategy + SPY benchmark). Each strategy a different color.

### Page 6 — Signals

**File:** `pages/6_Signals.py`  
**Purpose:** Why does the portfolio hold what it holds. Signal decomposition and strategy comparison at the ticker level. Not in original PRD — added because the 21-composite signal library makes this analysis possible and valuable for strategy selection decisions.  
**Refresh:** Manual.  
**IBKR connection:** Not required.

**Strategy selector** (top of page, single select): all strategies in `strategy_registry`. Default: active live strategy.

**Section A: Alpha Score Leaderboard**

For the selected strategy and latest `score_date`:

```sql
SELECT ticker, alpha_score, rank, universe_size
FROM alpha_scores
WHERE score_date = (SELECT MAX(score_date) FROM alpha_scores WHERE strategy_id = :sid)
  AND strategy_id = :sid
ORDER BY rank ASC
LIMIT 50;
```

Display top 25 and bottom 25 tickers as a table. Color top 25 green, bottom 25 red.

**Section B: Factor Breakdown (per ticker)**

Ticker selector (searchable): all tickers in the current universe.

For the selected ticker and strategy, display a horizontal bar chart (`st.bar_chart` or `st.pyplot`) of each factor's z-score contribution:
```sql
SELECT factor_name, z_score, raw_value
FROM factor_scores
WHERE ticker = :ticker
  AND score_date = (SELECT MAX(score_date) FROM factor_scores WHERE ticker = :ticker AND strategy_id = :sid)
  AND strategy_id = :sid
ORDER BY ABS(z_score) DESC;
```

Shows which factors are driving the alpha score (e.g., "momentum z-score = +1.8, value z-score = +0.4, quality z-score = -0.3").

**Section C: Factor Score History (30 days)**

Line chart of rolling z-scores for each factor for the selected ticker. One line per factor. Helps identify whether a high-ranking stock is recently improving or deteriorating.

**Section D: Strategy Registry**

Table of all strategies from `strategy_registry`:

| Column | Source |
|--------|--------|
| Strategy ID | `strategy_id` |
| Status | `status` (DRAFT / ACTIVE / VALIDATED / RETIRED) |
| Created | `created_at` |
| Last validated | From MLflow: last `search_runs()` tag `survival_funnel.passed = true` |
| OOS Sharpe | From MLflow: `metrics.oos_sharpe` on latest validated backtest run |
| Max DD (OOS) | From MLflow: `metrics.oos_max_drawdown` |
| Bootstrap 5th pct Sharpe | From MLflow: `tags.bootstrap_p05_sharpe` |
| Survival funnel | Pass/fail badge |

Status badges: DRAFT (grey), ACTIVE (blue), VALIDATED (green), RETIRED (dark grey).

**Section E: Cross-Strategy Alpha Overlap**

For the top N positions of each VALIDATED strategy, compute Jaccard similarity: `|A ∩ B| / |A ∪ B|`. Display as a heatmap. High overlap = strategies are not diversifying well against each other — relevant if you ever run multiple shadow portfolios.

### Page 7 — Audit Trail

**File:** `pages/7_Audit_Trail.py`  
**Purpose:** Immutable record of all fills, decisions, and compliance events. Read-only; no interactive mutations (C3 enforced — no UPDATE/DELETE paths in any query on this page).  
**Refresh:** Manual.  
**IBKR connection:** Not required.

**Section A: Fill History**

Filters: ticker (text), date range (date picker), strategy (select), side (BUY/SELL/All).

```sql
SELECT fill_id, fill_timestamp, ticker, strategy_id, side,
       filled_quantity, avg_fill_price, realized_pnl,
       cost_basis_per_share, wash_sale_disallowed, notes
FROM trade_fills
WHERE fill_timestamp BETWEEN :start AND :end
  AND (:ticker IS NULL OR ticker = :ticker)
  AND (:strategy_id IS NULL OR strategy_id = :strategy_id)
  AND (:side IS NULL OR side = :side)
ORDER BY fill_timestamp DESC
LIMIT 1000;
```

`st.dataframe` with column formatting:
- `realized_pnl`: red if negative, green if positive
- `wash_sale_disallowed`: red badge if true

**Section B: P&L Lineage (drill-down)**

Select a fill from the table → expand to show:
1. Fill details (all columns)
2. Alpha score for that ticker on that fill date for that strategy (join `alpha_scores`)
3. Factor scores for that ticker on that date for that strategy (join `factor_scores`) — shows what signals drove the trade decision
4. Blotter approval record for the run that produced this fill (join through `order_id` → `blotter_run_id` → `blotter_approvals`)

This is the F7.2 audit lineage requirement: given any fill, trace back to the exact signal score and strategy version that generated it.

**Section C: Wash-Sale History**

```sql
SELECT fill_id, fill_timestamp, ticker, filled_quantity, avg_fill_price,
       realized_pnl, wash_sale_disallowed
FROM trade_fills
WHERE side = 'SELL'
  AND (wash_sale_disallowed = true OR realized_pnl < 0)
ORDER BY fill_timestamp DESC;
```

**Section D: Blotter Approval History**

All rows from `blotter_approvals`, newest first. Columns: `blotter_run_id`, `approved_at_utc`, `approved_by`, `selected_order_ids` (count), `confirmed_blotter_sha256` (truncated), `dashboard_session_id`, `notes`.

Read-only. No edit controls. Enforces C3.
